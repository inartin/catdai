# Cadastral Lookup

## Stage
Implemented and active, with partial fallback.

Server-side 5xx outcomes from standalone searches are recorded as `error`, including failures after cached data is found. Retries update the same event outcome without resetting its timestamp or valuation progress. Unhandled application/credit errors return `internal_error` and a localized internal-error message, not the cadastral-provider outage message. Network failures still cannot establish whether the browser received a successful response.

## What It Does
- User enters a cadastral number in the valuation form.
- User can also add a cadastral number from the PDF export dialog when the current evaluation lacks official cadastral data.
- PDF-dialog cadastral lookup sends the same authenticated bearer token as the result page, so authenticated users receive full cadastral details there too.
- `/api/cadastral` requires a valid Supabase bearer token, then checks Redis, the long-lived Supabase cadastru store, the signed external cadastru worker, and returns 503 if the worker is unavailable. The in-app Geodata/cadastru.md backup is retained but disabled.
- Successful `/api/cadastral` responses are cached in Redis for 90 days by cadastral number and stored as one `cadastru_records` row per cadastral number with a 90-day refresh deadline. Saved snapshots return immediately after expiry while a background refresh runs; registry facts retain a 30-day refresh target. Failed/not-found responses are not cached.
- It autofills city, district, area, floor, total floors, building type, and bathroom count when available.
- Result and PDF cadastral panels show official apartment and building details when IPCBI provides them.
- Cadastral validation accepts apartment suffixes with 3 or 4 digits, including the UI example `0100201.999.01.0101`. Land parcels accept dotted seven-digit zones with 1–4 parcel digits, or 8–11 digits without a dot (for example, `1014203418` → `1014203.418`). Shared client validation, result-page requests and `/api/cadastral` normalize compact land inputs to dotted form before cache, storage and credit-key lookup; leading zeros are preserved.

## Address-Based Page

- `/ro/cadastru` and `/ru/cadastru` are the indexable localized search pages; direct `/cadastru` is a noindex duplicate that canonicals to the current language version.
- `/cadastru` lets users find official cadastral data by exact address or by entering a cadastral number directly. House numbers accept 1–4 digits with an optional `/` suffix of 1–4 digits or one Latin letter (`22`, `22/1`, `22/D`). The public/admin inputs retain letters and use the text keyboard. APIs normalize slash spacing and letter case; `/D` remains part of the exact address through source lookup, stored records and nearby origins, distinct from house `22`.

Query options such as `skipcache=true` and campaign tags survive; the path number, number-search source and a fresh lookup ID replace conflicting criteria, and `share_slug` is removed. ## Worker host failover

All six worker endpoints (cadastral number, address, nearby places, transport, municipal reports and 999 listing) try configured hosts in this order: `pi` → `mac` → `curiosity`. Set server-only values in the main CatDai app:

```env
CATDAI_API_PI_BASE_URL=https://cadastru-worker.catdai.md
CATDAI_API_MAC_BASE_URL=https://cadastru-worker-mac.catdai.md
CATDAI_API_CURIOSITY_BASE_URL=https://cadastru-worker-curiosity.catdai.md
CADASTRU_EXTERNAL_API_SECRET=the-same-secret-on-all-workers
```

These are deployment hostname choices; the two new Cloudflare tunnel routes must be created before they work. Unset or invalid host URLs are skipped and appear as Not configured in admin. Duplicate endpoint URLs are tried only once. Explicit per-host values take precedence over legacy settings; with no new settings, existing `CADASTRU_EXTERNAL_API_BASE_URL`/endpoint overrides still configure `pi`. Existing listing-specific URL and signing-secret overrides remain supported.

Failover is sequential and only handles unavailable worker hosts. A recognizable worker response (its node header or JSON result/error contract) stops host failover, including provider `service_unavailable`/5xx errors, rate limits, no-result, invalid-input, authentication and address-confirmation responses. A provider outage is not retried through other workers. Each attempt gets a fresh HMAC timestamp and request ID; lookup correlation stays the same and never enters the signed body. Existing usage telemetry records each real attempt, its configured target node, and safe returned node/version headers. No schema migration is required.

Network failures, lookup timeouts, gateway 5xx responses and unusable 2xx responses can be ambiguous. Before moving to the next host, CatDai checks the failed worker's `/health` once, with a five-second timeout, no cache and no credentials. If that endpoint returns `{ "ok": true }`, the original lookup error is returned without another worker call. Only a failed/invalid health check allows failover. HTTP 408/429 responses do not trigger host failover. Lookup timeouts still apply per attempted host, including response body reads; each possible failover can add up to five seconds for its health probe. Health probes create no usage events. There is no preflight/background routing poll or automatic provider lookup from the main app. Admin status checks remain independent and do not guarantee provider availability. Property persistence and credit authorization happen after the final lookup result, as before.

Run `pnpm exec node --experimental-vm-modules scripts/test-api-worker-fallbacks.mjs` and `pnpm exec node --experimental-vm-modules scripts/test-admin-worker-status.mjs` for isolated failover and health checks.

Snapshot refresh policy and migration/deployment details: see [Cadastru cache](cache.md#cadastru-cache). Refresh/scheduling checks: `pnpm exec node --experimental-vm-modules scripts/test-cadastru-refresh.mjs`.
