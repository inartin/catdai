## Analytics And Consent

- Live presence uses the existing browser ID: `OnlineUsersTracker` sends `POST /api/online-users` on entry, every 30 seconds while visible and immediately when returning to the tab. A browser counts once across tabs and public pages for 90 seconds after its last heartbeat; another browser/device counts separately, and blocked persistent storage cannot supply an ID. Admin routes and development Cadastru pages skip heartbeats. The existing authenticated statistics guard excludes marked admins and failed auth checks; recognized bots are excluded. Live counts remain transient Redis data. Accepted heartbeats also save latest browser/account activity in service-only `visitor_activity` under the runtime persistence rule, throttled to ten minutes with a reset at local midnight, for the dashboard's period-based Active Users count. Database failures are logged without disabling live presence. Public `GET /api/online-users` returns only the integer in plain text with `no-store`, never registers its caller or writes activity, and returns `503 Unavailable` if Redis fails. The POST returns the same count after an accepted heartbeat and rejects invalid browser IDs and cross-origin requests. See [Admin](admin.md#dashboard) for deduplication and rollout.
- Google tag loads once and configures `NEXT_PUBLIC_GA_ID` plus Google Ads-provided tag `AW-18184166002`. Loading is independent of auth/admin status; Google traffic exclusion is managed in Google, without an app policy request or session check.
- The shared Google tag script loads with the Ads ID first so Ads diagnostics see the expected source ID.
- CSP allows Google Ads collection endpoints used by remarketing, consent mode, and view-through conversion checks.
- CSP allows `https:` images so admin-authored news cover images and rich-description image links can render from external image hosts.
- CSP also allows `https://static.cloudflareinsights.com` so Cloudflare Web Analytics can inject its beacon script without violating `script-src` or `script-src-elem`.
- Default consent uses stored cookie consent when available, otherwise denies analytics/ad storage.
- Cookie banner can grant or deny consent.
- The `/estimeaza` submit button fires Google Ads conversion `AW-18184166002/Afy1CNv4g7McEPK08d5D` before navigating to `/evaluare`.
- `/estimeaza` sends `conversion_event_page_view_1` once on client mount when GA is available.
- Estimate logging stores device/session ids, input summary, result price, language, response time, and hashed IP.
- First-party usage tracking reuses the existing UUIDv4 `catdai-device-id` from localStorage and mirrors it to a one-year, SameSite=Lax cookie (`Secure` on HTTPS). Primary lookups and authenticated statistics helpers also send `x-catdai-device-id`, including when cookies are blocked. No IP or device fingerprint is used to join visitors; unavailable persistent storage produces no browser ID.
- `withStatisticsContext` carries a bounded, server-parsed `visitor` snapshot (`device_id`, `device_type`, `os`, `browser`) alongside the verified request user into deferred writers. Unknown device fields stay null and raw user-agent strings are not stored. Worker events use the server-resolved account when available. New anonymous API events are not attributed using legacy address/time heuristics. Admin suppression still applies before passive statistics are written; operational feedback/alerts keep their existing functionality. See [Admin](admin.md#dashboard) for tags and browser history.
- `/profile` exposes the authenticated user's own analytics rows in the paginated `Istoric` tab: `estimate_log` rows for sale/rent valuations and `cadastru_search_events` rows for cadastru searches. Cadastru rows show the cadastral number as the result plus search type, result type, lookup source, and district when available.
- Ad source tracking supports homepage entries through `/?src=zdg`, `/?utm_source=reddit`, and `/?utm_source=vtememd`. The 999.md tag `src=999` also starts tracking on any public page, including `/ro/cadastru/rezultat?share_slug=...&src=999` (use `&src=999` when the URL already has query parameters).
- When a supported source is seen on its entry page, the browser stores the source for the session and posts simple events to `/api/ad-source-events`. Tagged shared-report entries count as landing visits and retain their full entry path. Admin pages and development Cadastru pages remain excluded.
- `ad_source_events` is a separate Supabase table for this first-party trail: landing visit, later page views, landing CTA, estimate form view, estimate submit, estimate result view, and sign-in attachment.
- Authenticated tracking requests store `user_id` so ad sessions can be tied to registered Supabase users after login.
- CSP `connect-src` must include both `https://www.google-analytics.com` and `https://analytics.google.com` because GA4 can send collection requests to either host.
- Google Ads conversion and consent-mode pings can use `https://pagead2.googlesyndication.com`, so it is also allowed in `connect-src`.
- Admin ad-tracking top-card totals are computed per selected source and selected period from stored events; the visitor journey list is paged separately.
- Admin ad-tracking also counts distinct tracked registered users with a completed `paddle_payment_orders.status = 'paid'` order after their first stored event for the selected source and period, and marks those visitor journeys as bought. The main admin dashboard separately shows overall paid users across all sources, filtered to users who still have remaining paid feature credits.
- Runtime DB persistence for estimation logs, PDF events, cadastru search events, long-lived cadastru records, 999.md analysis events, shared links, favorites, and free monthly feature usage runs when `NODE_ENV=production` or `ENABLE_RUNTIME_PERSISTENCE=true`.
- In local `pnpm dev`, `/cadastru` and its localized/result routes skip Google tag configuration, ad-source events, checkout-popup events, and authenticated activity pings. Cadastru search and worker-usage statistics are also skipped while other pages follow their existing persistence rules.
- Calculator result usage is stored in `calculator_usage_events` under the same runtime persistence rule, including property filters, investment fields, tax selection, result rent/yield/payback metrics, and registered/anonymous attribution.
- `withStatisticsContext` in `src/lib/statistics-context.js` resolves current auth `app_metadata.catdai_is_admin` once per request and carries the collection policy through async/background work. Statistics writers check `shouldCollectStatistics`; routes that initiate worker calls use the same wrapper. Failed authenticated status checks suppress statistics. A new statistics-producing route must use this wrapper and predicate; runtime property caches and payment/credit accounting keep their separate persistence rules.
- Browser tracking helpers attach the current session bearer token, including news views, market-trends popups and secondary Cadastru requests. Signed-out visits remain anonymous and are tracked normally.
- Admin exclusion affects future statistics only. Operational favorites, shares and alerts store a creation-time `collect_statistics` flag; statistics queries use eligible rows while profile/favorite/share/alert functionality still uses all rows. Migration `20261019132539_admin_statistics_exclusion.sql` gives existing records the default `true`; no historical events are deleted or reclassified. Explicit news upvotes remain a user action, not passive view tracking.
- Cadastru shared-report clicks and unique opens are tracked separately from new searches, using `cadastru_share_events` and the report's verified originating search ID. The signed-in sharer's own opens are excluded; visitor/admin suppression is applied at event time and the report's creation-time eligibility is retained. Logged-out opens require a signed browser cookie returned to the server; no IP addresses or raw fingerprints are stored. Details and rollout: [Cadastru sharing](favorites-sharing.md#cadastru-reports).

## Payment ecommerce (MAIB)

The MAIB funnel uses the existing `NEXT_PUBLIC_GA_ID` Google tag. Custom events:

| Event | Trigger |
| --- | --- |
| `paid_offer_viewed` | A paid offer is visible (desktop/mobile variants are observed separately). |
| `checkout_button_clicked` | A feature or pricing checkout button is clicked. |
| `maib_pay_button_clicked` | Valid receipt email/Terms submission, after the buyer session is ready. |
| `sent_to_maib` | A bank checkout URL is available and the browser starts redirecting. |
| `returned_from_maib` | An authenticated status response matches a bank handoff recorded in this tab within 24 hours. |
| `checkout_error` | Guest session or checkout request failure; never a claim about bank settlement. |
| `payment_failed`, `payment_cancelled` | Backend-confirmed final MAIB outcomes. Pending, unknown and expired orders are not classified as failed. |

Standard `begin_checkout` fires once per checkout mount with a valid product; `purchase` and `refund` are backend-only. One ecommerce item represents the bought bundle, including custom single-use quantities. Purchases use immutable server order amounts/titles and the order UUID as `transaction_id`. Refund events contain only the newly refunded amount and the same transaction ID; partial refunds do not imply that a whole item was returned. MAIB field-level interactions remain outside the site's visibility. Paddle servicing is unchanged.

Browser collection requires production mode, `catdai.md`/`www.catdai.md`, the configured GA4 ID and granted cookie consent. Offers and checkout starts also respond to consent granted after rendering. Only consented GA-generated client/session IDs are attached to new production orders; absent IDs never block checkout. Server validation retains only bounded IDs and server-resolved buyer type/origin. Event payloads exclude receipt email, auth tokens, property searches and checkout query parameters. Events explicitly target GA4, leaving Google Ads conversion configuration separate.

Migration `20261102141624_ga4_payment_events.sql` adds nullable order context and a service-only, RLS-protected `ga4_payment_events` outbox. A trigger queues verified outcomes in the payment transaction; unique order/event keys prevent callback/poll duplicates and refund totals produce deltas. There is no historical backfill. The existing MAIB worker independently delivers the queue when `NODE_ENV=production`, `MAIB_ENVIRONMENT=production` and server-only `GA4_API_SECRET` are configured. Missing settings disable delivery. Restart the worker after deployment/config changes.

Purchases retry transient/uncertain delivery using their transaction ID. Uncertain refund delivery or an expired non-purchase sender lease becomes `unknown` for manual inspection instead of risking duplicated refunds. Explicit transient HTTP errors retry with backoff; other rejections require configuration review. Events older than Google's 72-hour window are skipped. `sent` means Google acknowledged receipt, not proof that it accepted the payload into reports. Validate payloads through `/debug/mp/collect` before rollout. Session attribution also depends on Google's session/time limits.

GA4 property setup:
- Use the existing Catdai web stream (`G-XD91H28TR6`); create a Measurement Protocol API secret and store it only in the worker's environment as `GA4_API_SECRET`.
- Create Event-scoped custom definitions: **Checkout origin** → `checkout_origin`, **Payment provider** → `payment_provider`, **Buyer type** → `buyer_type`, **Checkout error reason** → `checkout_error_reason`. Standard item/revenue fields need no custom definitions.
- List `checkout.maib.md` as an unwanted referral. Keep `purchase` as a key event; clicks remain funnel steps.
- Create a Funnel Exploration: `checkout_button_clicked` → `begin_checkout` → `maib_pay_button_clicked` → `sent_to_maib` → `purchase`, allowing intervening events. `returned_from_maib` is diagnostic and is not required for purchase completion. Standard checkout reports expecting on-site card/shipping entry do not represent this hosted checkout; use the custom funnel.

Checks: `pnpm exec node --experimental-vm-modules scripts/test-ga4-payments.mjs`, the MAIB continue/result and guest checkout suites, and `pnpm build`. Google DebugView/Realtime and a real consented production payment are separate rollout checks. Existing internal payment statistics retain their event names and reporting behavior.

Rollout on 2 November 2026: the outbox migration was applied to the shared Catdai database and verified (RLS enabled, client roles denied table/function access, invoker functions, no historical events). The four custom dimensions and **CatDai - MAIB payment funnel** exploration were saved in GA4. With owner approval, Google's User Data Collection Acknowledgement was accepted and the **CatDai payments** API secret was created. `GA4_API_SECRET` is stored in ignored `.env.local` files locally and on production `aws2` (`0600`); no value is stored in code or documentation. Google's strict `/debug/mp/collect` validation returned no messages for purchase, partial refund, confirmed failure and cancellation payloads; debug requests do not populate reports or verify secret authentication. The production worker still has the previous code, so application/worker deployment and a real consented payment remain required. The embedded Google tag settings panel loaded blank, so MAIB referral exclusion could not yet be saved.
